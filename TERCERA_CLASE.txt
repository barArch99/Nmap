TEMA 4: PUERTOS Y SOCKETS
==================================================================================================

   •   Repaso: la IP identifica al EQUIPO; el PUERTO identifica al SERVICIO/PROCESO dentro
       de ese equipo. Es un numero de 16 bits → 0 a 65535, separado para TCP y para UDP
       (el 53/tcp y el 53/udp son puertos distintos).

       Rangos:
           0 - 1023        Bien conocidos (well-known): 22 SSH, 53 DNS, 80 HTTP, 443 HTTPS
                           En Linux solo root puede escuchar en ellos.
           1024 - 49151    Registrados: 3306 MySQL, 3389 RDP, 8080 HTTP alterno
           49152 - 65535   Dinamicos / efimeros: los usa el CLIENTE como puerto de origen
                           (en Linux el rango real: cat /proc/sys/net/ipv4/ip_local_port_range)

   •   SOCKET: es el "extremo" de una comunicacion. Se forma con:
               IP + PUERTO + PROTOCOLO        ej.  192.168.1.11:4444/tcp

       Una CONEXION TCP queda identificada por 4 datos (la "4-tupla"):
               IP origen : puerto origen  ↔  IP destino : puerto destino
               192.168.1.11:51234         ↔  142.250.1.1:443

       Por eso un servidor web puede atender miles de clientes en el MISMO puerto 443:
       cada cliente trae un par (IP, puerto origen) distinto → socket distinto.

       Analogia: la IP es el edificio, el puerto es el numero de apartamento, y el socket
       es la llamada concreta entre un apartamento y otro.

   •   Estados de un socket (los que veras con ss):
           LISTEN        un programa esta esperando conexiones en ese puerto (servidor)
           ESTAB         conexion establecida (handshake completado)
           TIME-WAIT     conexion cerrada, el sistema espera un poco antes de liberarla
           UNCONN        socket UDP (UDP no tiene "conexion", solo esta abierto)

   •   Por que importa para Nmap: un puerto "open" en Nmap = hay un socket en LISTEN en el
       objetivo. "closed" = el equipo responde pero nadie escucha ahi (RST). "filtered" =
       un firewall no deja saber.

   --------------------------------------------------------------------------------------------------
   Comandos de la practica: que hace cada uno
   --------------------------------------------------------------------------------------------------

   ss -tulnp
       ss = "socket statistics": lista los sockets del sistema (reemplazo moderno de netstat).
           -t  sockets TCP
           -u  sockets UDP
           -l  solo los que estan en LISTEN (esperando conexiones = servicios/servidores)
           -n  numerico: muestra 22 en vez de "ssh" y la IP en vez del nombre (mas rapido)
           -p  muestra el proceso (programa + PID) dueño del socket; sin sudo solo ves los tuyos
       Columnas: Local Address:Port = donde escucha. 0.0.0.0 = en todas las interfaces;
       127.0.0.1 = solo accesible desde el propio equipo.

   nc -lvnp 4444
       nc (netcat) = "navaja suiza" de red: abre conexiones TCP/UDP a mano.
           -l  modo escucha (actua como SERVIDOR)
           -v  verbose: avisa cuando alguien se conecta
           -n  no resolver nombres DNS
           -p 4444  puerto donde escuchar
       Resultado: crea un socket en LISTEN en 0.0.0.0:4444.

   ss -tlnp | grep 4444
       Lista solo sockets TCP en LISTEN y el | grep 4444 filtra la linea del puerto 4444.
       Sirve para COMPROBAR que el nc de arriba realmente esta escuchando.

   nc 127.0.0.1 4444
       nc sin -l actua como CLIENTE: se conecta a 127.0.0.1 (loopback = tu propio equipo)
       en el puerto 4444. Hace el three-way handshake. Lo que escribas aparece en la otra
       terminal (y al reves): es un chat por un socket TCP.

   ss -tnp | grep 4444
       Sin -l: muestra conexiones ACTIVAS (ESTAB), no las que escuchan. Aparecen 2 lineas,
       una por cada extremo:
           127.0.0.1:4444  ↔ 127.0.0.1:5XXXX   (lado servidor)
           127.0.0.1:5XXXX ↔ 127.0.0.1:4444    (lado cliente)
       El 5XXXX es el puerto EFIMERO que el sistema asigno al cliente → la 4-tupla.

   nmap -p 4444 127.0.0.1
       Escanea solo el puerto 4444 de tu propia maquina.
           Con nc escuchando  → 4444/tcp open   (hay socket LISTEN, responde SYN-ACK)
           Sin nc (Ctrl+C)    → 4444/tcp closed (el kernel responde RST, nadie escucha)
       Demuestra en vivo la relacion socket LISTEN ↔ puerto open.

   cat /proc/sys/net/ipv4/ip_local_port_range
       /proc es un sistema de archivos virtual donde el kernel expone su configuracion.
       Este archivo contiene 2 numeros: el primer y ultimo puerto que Linux usa como
       puertos efimeros (de origen) para conexiones salientes. En Linux suele ser
       32768 60999 (distinto al rango "oficial" 49152-65535).

   Practica y resultados propios
   --------------------------------------------------------------------------------------------------
   1) ss -tulnp
       Netid  State  Recv-Q  Send-Q  Local Address:Port  Peer Address:Port  Process
       (sin ninguna fila)

       - Resultado: mi equipo (BlackArch) NO tiene ningun socket TCP ni UDP en LISTEN → no
         expone ningun servicio. Arch/BlackArch no activa servicios (sshd, etc.) por defecto:
         hay que habilitarlos a mano con systemctl.
       - Consecuencia: si alguien le hace nmap a 192.168.1.11 veria todos los puertos
         closed (o filtered si hubiera firewall). Superficie de ataque minima.
       - Columnas: Recv-Q/Send-Q = datos en cola de recepcion/envio; Peer Address = el
         otro extremo (en LISTEN sale *:* porque aun no hay nadie conectado).

   2) nc -lvnp 4444   +   ss -tlnp | grep 4444
       LISTEN 0      1            0.0.0.0:4444      0.0.0.0:*    users:(("nc",pid=20355,fd=3))

       - LISTEN          el socket esta esperando conexiones.
       - Recv-Q = 0      en un socket LISTEN: conexiones que ya completaron el handshake y
                         esperan a que el programa las acepte (ninguna todavia).
       - Send-Q = 1      en un socket LISTEN: es el BACKLOG, el maximo de conexiones en cola.
                         nc lo pone en 1 porque solo atiende a un cliente.
       - 0.0.0.0:4444    escucha en TODAS las interfaces (lo, wlan0...) → accesible desde la
                         LAN, no solo desde el propio equipo.
       - 0.0.0.0:*       Peer vacio: aun no hay nadie conectado.
       - nc pid=20355    el proceso dueño del socket (se podria matar con kill 20355).
       - fd=3            file descriptor: en Linux "todo es un archivo"; 0,1,2 son stdin,
                         stdout y stderr, asi que el socket recibe el siguiente libre: el 3.

   3) nc 127.0.0.1 4444   +   ss -tnp | grep 4444      (conexion establecida)
       ESTAB  0  0  127.0.0.1:4444   127.0.0.1:37408  users:(("nc",pid=27366,fd=4))  ← servidor
       ESTAB  0  0  127.0.0.1:37408  127.0.0.1:4444   users:(("nc",pid=27370,fd=3))  ← cliente

       - 2 lineas = los 2 extremos de UNA conexion (cada uno es un socket).
       - La 4-tupla: 127.0.0.1:37408 ↔ 127.0.0.1:4444
       - 37408 = puerto EFIMERO que Linux eligio para el cliente (esta dentro del rango
         32768-60999 del paso 7).
       - El servidor ahora usa fd=4: el fd=3 sigue siendo el socket LISTEN, y al aceptar la
         conexion el kernel crea un socket NUEVO (fd=4) solo para ese cliente. Asi un
         servidor atiende a varios clientes: 1 socket LISTEN + 1 socket por conexion.

   4) nmap -p 4444 127.0.0.1
       Con nc escuchando:   4444/tcp open    krb524
       Sin nc (cerrado):    4444/tcp closed  krb524

       - open = hay socket LISTEN (responde SYN-ACK); closed = nadie escucha (RST).
       - OJO: "krb524" NO es lo que corre ahi (era nc). Nmap solo pone el nombre que tiene
         ese numero en su tabla /usr/share/nmap/nmap-services. Para saber el servicio REAL
         hace falta -sV (deteccion de versiones, Semana 3 del plan).

   5) ss -tan | grep 4444   (justo despues de cerrar)
       TIME-WAIT  0  0  127.0.0.1:4444  127.0.0.1:37408

       - La conexion ya termino pero el sistema la retiene unos segundos (~60 s en Linux)
         por si llegan paquetes rezagados. Luego desaparece sola.

   6) cat /proc/sys/net/ipv4/ip_local_port_range
       32768   60999
       - Rango de puertos efimeros de Linux (distinto al oficial IANA 49152-65535).
         El 37408 del paso 3 cae dentro de este rango.

   --------------------------------------------------------------------------------------------------
   Conclusiones del Tema 4
   --------------------------------------------------------------------------------------------------
       - Puerto = numero (0-65535) por protocolo; socket = IP + puerto + protocolo.
       - Una conexion TCP = 4-tupla; el cliente usa un puerto efimero aleatorio.
       - Servidor: 1 socket LISTEN + 1 socket nuevo por cada cliente aceptado.
       - Nmap "open" = socket LISTEN en el objetivo; "closed" = RST.
       - El nombre del servicio que muestra Nmap sin -sV es solo una suposicion por numero.
       - ss es la herramienta para ver sockets propios: -tulnp (servicios), -tnp (conexiones).

TEMA 5: ICMP (REPASO APLICADO A NMAP)
==================================================================================================

   •   ICMP (Internet Control Message Protocol): protocolo de MENSAJES DE CONTROL y ERROR de
       la capa de red (va dentro de IP, igual que TCP y UDP, pero NO usa puertos).
       No transporta datos de aplicaciones: sirve para que los equipos se avisen cosas como
       "estoy vivo", "no llego a ese destino", "ese puerto esta cerrado", "el paquete murio".

   •   Cada mensaje tiene TIPO y CODIGO. Los importantes:

           Tipo  Nombre                      Para que se usa
           ----  --------------------------  ----------------------------------------------
            8    Echo Request                ping (pregunta "¿estas vivo?")
            0    Echo Reply                  respuesta al ping
            3    Destination Unreachable     no se pudo entregar. Codigos clave:
                   code 1  Host unreachable       el host no existe / no responde en la LAN
                   code 3  PORT unreachable       puerto UDP CERRADO
                   code 13 Admin prohibited       un FIREWALL lo bloqueo
           11    Time Exceeded               el TTL llego a 0 (lo usa traceroute/tracepath)
           13/14 Timestamp Request/Reply     otra forma de preguntar "¿estas vivo?"

   •   Recordatorio TTL (Segunda Clase): cada router resta 1. Cuando llega a 0 el router
       descarta el paquete y devuelve ICMP tipo 11. tracepath/traceroute aprovechan esto:
       mandan paquetes con TTL=1, 2, 3... y cada router que responde revela un salto.

   •   COMO LO USA NMAP (lo importante de este tema):

       1) Descubrimiento de hosts (-sn):
            - En la LAN y como root → usa ARP (Segunda Clase), no ICMP.
            - Fuera de la LAN y como root, por defecto manda 4 sondas:
                  ICMP echo (tipo 8) + TCP SYN al 443 + TCP ACK al 80 + ICMP timestamp (13)
              Si CUALQUIERA responde → host "up".
            - Opciones para elegir la sonda ICMP:
                  -PE  echo request      -PP  timestamp      -PM  address mask
            - Si un firewall bloquea el ping, Nmap puede creer que el host esta caido →
              -Pn = "no hagas descubrimiento, asume que esta vivo y escanea igual".

       2) Escaneo UDP (-sU): explica el problema visto en la Segunda Clase:
            - Puerto UDP cerrado → el objetivo responde ICMP tipo 3 code 3 → "closed"
            - Respuesta ICMP tipo 3 con otro codigo (ej. 13) → "filtered" (firewall)
            - Sin respuesta → "open|filtered" (no se puede distinguir)
            - Linux limita cuantos ICMP de error envia por segundo → por eso -sU es LENTO.

       3) Estado "filtered" en TCP: si en vez de SYN-ACK o RST llega un ICMP
          "unreachable" (tipo 3), Nmap marca el puerto como filtered.

   --------------------------------------------------------------------------------------------------
   Subtema: ¿Que es y para que sirve tcpdump?
   --------------------------------------------------------------------------------------------------
   •   tcpdump es un CAPTURADOR DE PAQUETES (sniffer) de terminal. Pone la tarjeta a "escuchar"
       y muestra cada paquete que entra o sale: origen, destino, protocolo, flags, tamaño.
       Es como la version de terminal de Wireshark (ambos usan la libreria libpcap).
       Ya se uso en la Segunda Clase (Kali) para ver el handshake TCP y un datagrama UDP.

   •   Para que sirve:
       - VER lo que realmente pasa por la red en vez de suponerlo (ej. que manda Nmap y que
         le responde el objetivo).
       - Diagnosticar problemas (¿sale el paquete? ¿llega respuesta? ¿quien no contesta?).
       - Aprender protocolos (ARP, ICMP, TCP, UDP, DNS, DHCP) viendolos en vivo.
       - Guardar capturas en .pcap para analizarlas despues en Wireshark.

   •   Necesita sudo: capturar exige poner la interfaz en modo promiscuo/acceso crudo.

   •   Opciones basicas:
           -i enp8s0     interfaz a escuchar (-i any = todas, -i lo = loopback)
           -n            no traducir IPs a nombres (mas rapido y sin generar trafico DNS)
           -c 10         capturar 10 paquetes y parar (si no, Ctrl+C)
           -v / -vv      mas detalle (TTL, longitud, flags IP...)
           -e            mostrar tambien las MAC (capa 2)
           -w cap.pcap   guardar en archivo      -r cap.pcap   leer un archivo guardado
           -A / -X       mostrar el contenido del paquete (ASCII / hex+ASCII)

   •   Filtros (se escriben al final, sintaxis BPF):
           icmp                     solo ICMP
           arp                      solo ARP
           tcp / udp                por protocolo
           port 53                  un puerto (origen o destino)
           host 192.168.1.1         trafico desde/hacia esa IP
           net 192.168.1.0/24       toda una red
           combinables: and, or, not →  host 192.168.1.1 and icmp

   •   Ejemplos:
           sudo tcpdump -i enp8s0 -n icmp                 pings entrando y saliendo
           sudo tcpdump -i enp8s0 -n port 53              consultas DNS
           sudo tcpdump -i enp8s0 -n host 192.168.1.1 -c 20
           sudo tcpdump -i enp8s0 -w captura.pcap         guardar para Wireshark

   •   Como leer una linea:
           12:00:01.123 IP 192.168.1.20 > 192.168.1.1: ICMP echo request, id 5, seq 1, length 64
           hora         IP origen      > IP destino : protocolo y detalle

   •   Etica: solo capturar en tus equipos/redes o con autorizacion; en una red ajena
       puede verse trafico de otras personas.

   --------------------------------------------------------------------------------------------------
   Practica y resultados propios
   --------------------------------------------------------------------------------------------------
   Equipo hoy: BlackArch por CABLE (enp8s0), IP 192.168.1.20/24, gateway 192.168.1.1

   Idea base: "capturar trafico" = ver cada paquete (sobre con origen, destino, tipo y
   contenido) que entra/sale de la tarjeta. Dos formas:
       nmap --packet-trace  → solo los paquetes de Nmap
       tcpdump              → todo lo que pasa por la interfaz
   En --packet-trace:  SENT = paquete ENVIADO (yo → objetivo)
                       RCVD = paquete RECIBIDO (objetivo → yo)
       SENT sin RCVD = nadie contesto (apagado, no existe o firewall).

   1) nmap -sn --packet-trace 192.168.1.1   (como root)
       SENT (0.0092s) ARP who-has 192.168.1.1 tell 192.168.1.20
       RCVD (0.0136s) ARP reply 192.168.1.1 is-at 44:48:B9:A4:22:10
       NSOCK INFO ... UDP connection requested to 200.21.200.80:53
       NSOCK INFO ... UDP connection requested to 200.21.200.10:53
       NSOCK INFO ... Write request for 42 bytes ... [200.21.200.80:53]
       NSOCK INFO ... READ SUCCESS ... [200.21.200.80:53] (119 bytes)
       Host is up (0.0044s latency).
       MAC Address: 44:48:B9:A4:22:10 (MitraStar Technology)

       - Descubrimiento: 1 SENT (ARP who-has) + 1 RCVD (ARP reply) → host up.
         Como el router esta en la LAN, Nmap uso ARP y NO ICMP.
         0.0136 - 0.0092 = 0.0044 s → la "latency" de 4.4 ms que reporta.
       - MitraStar Technology = fabricante del router (sacado del OUI de la MAC 44:48:B9).
       - Lineas NSOCK = DNS INVERSO: Nmap pregunta por UDP puerto 53 a los servidores DNS
         configurados (200.21.200.80 y 200.21.200.10, IPs publicas → DNS del proveedor de
         internet) "¿que nombre tiene 192.168.1.1?". Mando 42 bytes, recibio 119 de respuesta.
         No es parte del descubrimiento; es solo para poner nombre al host.
         Con -n se desactiva (mas rapido y no genera trafico DNS). → Se vera en Tema 6.
       - Escaneo previo de toda la red (nmap -sn 192.168.1.0/24): aparecio otra MAC
         aleatoria (3A:62:... → segundo digito A) y otro equipo MitraStar en 192.168.1.48.

   2) nmap -sn -PE --disable-arp-ping -n --packet-trace 192.168.1.1   (forzar ICMP)
       SENT (0.0079s) ICMP [192.168.1.20 > 192.168.1.1 Echo request (type=8/code=0) id=21728 seq=0]
                      IP [ttl=42 id=39751 iplen=28 ]
       RCVD (0.0127s) ICMP [192.168.1.1 > 192.168.1.20 Echo reply (type=0/code=0) id=21728 seq=0]
                      IP [ttl=64 id=20042 iplen=28 ]
       Host is up (0.0049s latency).

       Opciones: -PE = descubrir con ICMP echo · --disable-arp-ping = no usar ARP ·
                 -n = sin DNS inverso (desaparecen las lineas NSOCK).

       Parte ICMP:
       - type=8/code=0 → Echo Request (pregunta).  type=0/code=0 → Echo Reply (respuesta).
       - id=21728 y seq=0 son IGUALES en ambos: asi Nmap sabe que esa respuesta corresponde
         a SU pregunta (si mandara varios, seq iria 0, 1, 2...).
       Parte IP:
       - ttl=42 (enviado): NO es el 64 normal de Linux. Nmap construye el paquete a mano y
         elige un TTL aleatorio → un IDS atento puede notar que "no es un ping normal".
       - ttl=64 (recibido): el router responde con 64 intacto → esta a 0 saltos (misma LAN)
         y su sistema probablemente es Linux/embebido (64 inicial).
       - iplen=28 = 20 bytes cabecera IP + 8 bytes cabecera ICMP, SIN datos.
         (El comando ping normal manda 84: 20 + 8 + 56 de relleno.)
       - id (IP) = numero de identificacion del paquete, distinto en cada lado.
       - 0.0127 - 0.0079 ≈ 4.9 ms = latency. Aun asi muestra la MAC porque el router
         esta en la LAN (el kernel la conoce por su cache ARP).

       Comparacion ARP vs ICMP contra el mismo router: ambos dan "up" con ~4-5 ms.
       En la LAN Nmap prefiere ARP porque un firewall puede bloquear ICMP, pero ningun
       equipo puede ignorar ARP si quiere comunicarse en la red.

   3) nmap -sn -PE --disable-arp-ping -n --packet-trace 192.168.1.250   (IP sin equipo)
       SENT (0.0142s) ICMP [192.168.1.20 > 192.168.1.250 Echo request (type=8/code=0) id=10105 seq=0] IP [ttl=43 ...]
       SENT (1.0144s) ICMP [192.168.1.20 > 192.168.1.250 Echo request (type=8/code=0) id=3969 seq=0]  IP [ttl=50 ...]
       Note: Host seems down. If it is really up, but blocking our ping probes, try -Pn
       Nmap done: 1 IP address (0 hosts up) scanned in 2.03 seconds

       - 2 SENT y 0 RCVD → nadie contesto → "Host seems down".
       - Nmap no se rinde al primer intento: espera ~1 s y REINTENTA (1.0144 - 0.0142 ≈ 1 s).
         Tras el 2º intento espera otro ~1 s → total 2.03 s (vs 0.06 s cuando si contesta).
         Por eso escanear rangos con muchas IPs vacias es lento.
       - Cada intento usa id y ttl distintos (43, 50): Nmap los aleatoriza en cada paquete.
       - Sin respuesta tampoco hay MAC ni fabricante.
       - "seems down" = PARECE caido. Nmap no puede distinguir entre:
             a) no hay ningun equipo en esa IP
             b) hay un equipo, pero un firewall descarta los ping (ICMP)
         Por eso sugiere -Pn: saltarse el descubrimiento y escanear puertos igualmente.

   Resumen descubrimiento con ICMP:
       SENT + RCVD Echo reply     → up
       SENT + SENT (sin RCVD)     → seems down (apagado, inexistente o ICMP bloqueado)
       Duda por firewall          → -Pn

         se detenia), 0 dropped (no se perdio ninguno).

   Paso 4) ss -tnp | grep 160.79.104.10   (¿que programa es dueño de esa conexion?)
       ESTAB 0 0  192.168.1.20:39054  160.79.104.10:443  users:(("claude",pid=18757,fd=12))
       ESTAB 0 0  192.168.1.20:43748  160.79.104.10:443  users:(("claude",pid=18757,fd=16))

       - El puerto 39054 es EXACTAMENTE el que aparecio en la captura de tcpdump → misma
         conexion. El dueño es el proceso "claude" (Claude Code, pid 18757) hablando con
         los servidores de Anthropic por HTTPS.
       - Un mismo programa tiene 2 conexiones (2 sockets, fd 12 y fd 16) al mismo servidor,
         cada una con su propio puerto efimero (39054 y 43748).
       - Metodo aprendido:  tcpdump → QUE IPs/puertos hablan
                            ss -tnp → QUE PROGRAMA tiene ese socket
         (util para detectar conexiones sospechosas en tu equipo).

   Paso 5) Filtro:  Terminal 1: tcpdump -i enp8s0 -n icmp   ·   Terminal 2: ping -c 2 192.168.1.1
       16:04:48.372019 IP 192.168.1.20 > 192.168.1.1: ICMP echo request, id 54810, seq 1, length 64
       16:04:48.381898 IP 192.168.1.1 > 192.168.1.20: ICMP echo reply, id 54810, seq 1, length 64
       16:04:49.373224 IP 192.168.1.20 > 192.168.1.1: ICMP echo request, id 54810, seq 2, length 64
       16:04:49.377687 IP 192.168.1.1 > 192.168.1.20: ICMP echo reply, id 54810, seq 2, length 64

       - El filtro "icmp" funciono: no aparece NADA de HTTPS (las conexiones de claude
         siguen activas, pero tcpdump las descarta).
       - Sin tcpdump esperando no se ve nada: se queda "listening" hasta que haya trafico
         que cumpla el filtro; sin -c se detiene con Ctrl+C.
       - IPs SIN puerto (192.168.1.20 > 192.168.1.1): ICMP no usa puertos.
       - Pareja request/reply con el mismo seq → cada pregunta tiene su respuesta.
       - id 54810 igual en todo el ping (identifica ESTE comando ping); seq sube 1, 2.
         (ping empieza en seq 1; Nmap empezo en seq 0.)
       - Separacion de 1 s entre request (48.37 → 49.37): ping manda uno por segundo.
       - Tiempo de respuesta: 48.381898 - 48.372019 ≈ 9.9 ms ; 49.377687 - 49.373224 ≈ 4.5 ms
       - length 64 = 8 cabecera ICMP + 56 datos de relleno (con IP: 84 bytes).
         Nmap mando iplen=28 (sin datos) → un ping de Nmap y uno normal SE DISTINGUEN.

   Paso 6) Puerto UDP cerrado = ICMP port unreachable
       Terminal 1: sudo tcpdump -i lo -n icmp      Terminal 2: sudo nmap -sU -p 9999 127.0.0.1

       Terminal 2:  9999/udp closed distinct      (latency 0.000051s)
       Terminal 1:  16:10:16.490045 IP 127.0.0.1 > 127.0.0.1: ICMP 127.0.0.1 udp port 9999 unreachable, length 36

       - 1er intento no salio nada en tcpdump: hay que arrancar tcpdump ANTES del escaneo y
         en la interfaz correcta (lo, porque el trafico a 127.0.0.1 nunca sale por el cable).
       - Esta es la PRUEBA de por que Nmap dice "closed" en UDP: el sistema respondio
         ICMP tipo 3 code 3 (Destination/Port Unreachable) = "nadie escucha en ese puerto".
       - Origen y destino 127.0.0.1: el kernel se responde a si mismo (loopback).
       - length 36 = 8 cabecera ICMP + 20 cabecera IP original + 8 cabecera UDP original.
         El ICMP de error COPIA el inicio del paquete que fallo → asi Nmap sabe a cual de
         sus sondas corresponde (puerto 9999).
       - "distinct" = nombre del 9999 en la tabla de Nmap, no el servicio real.
       - Sin este ICMP (firewall que lo descarta) el resultado seria "open|filtered".

   Paso 7) Pregunta + respuesta juntas (filtro combinado con "or")
       Terminal 1: sudo tcpdump -i lo -n 'icmp or udp port 9999'
       Terminal 2: sudo nmap -sU -p 9999 127.0.0.1

       16:11:52.053925 IP 127.0.0.1.46868 > 127.0.0.1.9999: UDP, length 0
       16:11:52.053947 IP 127.0.0.1 > 127.0.0.1: ICMP 127.0.0.1 udp port 9999 unreachable, length 36

       - Linea 1 = la SONDA de Nmap: UDP desde el puerto 46868 (origen) al 9999 (destino).
         length 0 → datagrama VACIO. Para puertos que no conoce Nmap manda UDP sin datos;
         para puertos conocidos (53 DNS, 123 NTP...) manda una consulta real de ese
         protocolo para provocar respuesta.
       - Linea 2 = la RESPUESTA del kernel: ICMP port unreachable → "closed".
       - 053947 - 053925 = 22 microsegundos (todo dentro del mismo equipo).
       - Filtros: 'icmp or udp port 9999' → "o uno o el otro". Comillas para que bash no
         interprete el filtro. Tambien existen "and" y "not".
       - Error comun visto: tcpdump -i snp8s0 (typo) → la interfaz no existe.

   --------------------------------------------------------------------------------------------------
   Conclusiones del Tema 5
   --------------------------------------------------------------------------------------------------
       - ICMP = mensajes de control/error dentro de IP, sin puertos. Tipo + codigo.
       - Nmap -sn: en LAN usa ARP; con -PE usa ICMP echo (8 → 0). Sin respuesta tras 2
         intentos → "seems down" (no distingue apagado de firewall → -Pn).
       - --packet-trace muestra lo que Nmap envia (SENT) y recibe (RCVD).
       - El ping de Nmap es distinto a un ping normal (sin datos, TTL aleatorio, seq 0).
       - UDP cerrado = ICMP tipo 3 code 3 (port unreachable); sin respuesta = open|filtered.
       - tcpdump: -D (interfaces), -i (interfaz), -n (sin DNS), -c (cantidad), filtros
         (icmp, udp port N, host IP, or/and/not). Arrancarlo ANTES del trafico.
       - tcpdump dice QUE hablan (IP/puerto); ss -tnp dice QUE PROGRAMA.

==================================================================================================
TEMA 6: DNS, DHCP, GATEWAY Y NAT
==================================================================================================
   (fecha: 2026-11-09 - archivo propio: TEMA_6_DNS_DHCP_Gateway_NAT.txt)

   •   GATEWAY (puerta de enlace): la SALIDA de mi red hacia otras redes (internet).
       Casi siempre es el router. Todo paquete cuyo destino NO esta en mi red local se le
       entrega al gateway para que lo saque. En la tabla de rutas es la ruta "default".

   •   DNS (Domain Name System): traduce NOMBRES a IPs (como una agenda de contactos).
       Yo escribo scanme.nmap.org, pero la red solo entiende 45.33.32.156.
           - Puerto 53. Sobre todo UDP (consultas normales, rapidas, sin conexion).
             TCP 53 solo para respuestas grandes y TRANSFERENCIAS DE ZONA (copiar todos
             los registros de un dominio → muy usado en pentesting).
           - /etc/resolv.conf   → A QUE servidor DNS preguntar (linea "nameserver").
           - /etc/hosts         → "agenda manual" nombre → IP que se consulta ANTES del DNS
                                  (ahi esta 127.0.0.1 localhost y ahi se pone unika.htb en HTB).
           - Tipos de registro:
                 A      nombre → IPv4
                 AAAA   nombre → IPv6
                 PTR    IP → nombre (busqueda INVERSA)
                 MX     servidor de correo del dominio
                 NS     servidores DNS que mandan sobre el dominio
                 SOA    "quien manda" en la zona (autoridad)
           - NXDOMAIN = "Non-Existent Domain": ese nombre no existe.

   •   DHCP (Dynamic Host Configuration Protocol): cuando me conecto a la red no tengo
       IP, gateway ni DNS. Mi PC "grita" a la red pidiendo configuracion y el servidor
       DHCP (el router) me la PRESTA por un tiempo → eso se llama LEASE (prestamo).
           - Un solo prestamo entrega: IP + mascara, gateway, DNS y duracion.
           - A la MITAD del tiempo el PC pide RENOVAR (normalmente le dan la misma IP).
           - En Linux la IP prestada aparece como "dynamic"; puesta a mano = "permanent".

   •   NAT (Network Address Translation): mi IP privada (192.168.x.x) NO existe en
       internet (millones de casas tienen la misma). El router CAMBIA mi IP privada por
       SU IP PUBLICA al sacar el paquete, y al volver la respuesta la devuelve a mi PC.
           - Todos los equipos de la casa salen con la MISMA IP publica.
           - Nadie de afuera puede INICIAR una conexion a mi PC: el router no sabria a
             cual equipo mandarla (como la porteria de un edificio).
           - VirtualBox en modo NAT hace lo mismo con la VM (gateway virtual 10.0.2.2);
             en modo PUENTE (bridged) la VM es un equipo mas de la red (gateway 192.168.1.1).
           - En HTB la victima no ve mi IP de casa: ve mi IP de la VPN (tun0).

   •   COMO SE RELACIONA CON NMAP:
       - Sin -n, Nmap hace un DNS INVERSO (PTR) por cada IP que escanea (las lineas NSOCK
         del Tema 5). 256 IPs = 256 consultas → -n acelera y hace menos ruido.
       - scanme.nmap.org es el servidor que Nmap AUTORIZA para practicar.
       - Desde fuera, un escaneo a mi IP publica choca con el ROUTER (NAT), no con mi PC.

   --------------------------------------------------------------------------------------------------
   Practica y resultados propios (estilo HTB: pregunta → como lo encontre → respuesta)
   --------------------------------------------------------------------------------------------------
   Equipo: BlackArch por CABLE (enp8s0). Se hizo en mi propio equipo (sistema autorizado).

   Task 1) ¿Cual es la IP del gateway?
       ip route  → linea "default via ..."
       Respuesta: 192.168.1.1 (el router de la casa)

   Task 2) ¿El gateway responde?
       ping -c 5 192.168.1.1

       64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=4.31 ms
       ...
       5 packets transmitted, 5 received, 0% packet loss, time 4004ms
       rtt min/avg/max/mdev = 4.305/4.442/4.630/0.115 ms

       - -c 5 = mandar solo 5 paquetes (si no, sigue para siempre).
       - 5 enviados, 5 recibidos, 0% perdidos. Promedio (avg) 4.442 ms.
       - ttl=64 → Linux suele empezar en 64 (Windows en 128): el router corre Linux por dentro.
       - ~4 ms es normal en la misma red; un sitio de internet suele tardar 20 ms o mas.

   Task 3) ¿Cual es la IP del servidor DNS?
       cat /etc/resolv.conf

       # Generated by NetworkManager
       nameserver 200.21.200.10
       nameserver 200.21.200.80

       - Dos DNS: el primero y uno de RESPALDO si el primero no responde.
       - Son IPs PUBLICAS → DNS del proveedor de internet (los mismos del Tema 5).
       - Lo genera NetworkManager → no editarlo a mano (lo reescribe).
       - Error mio: primero respondi 127.0.0.1 porque lei /etc/hosts (localhost), que es
         otro archivo. Comprobado con sudo ss -tulnp: NO hay nada escuchando en el puerto
         53 de mi equipo, asi que no hay DNS local.
       - Error mio 2: corri "sudo ss -tulnp" y "grep :53" por separado; sin el | (pipe)
         grep se queda esperando texto. Correcto: sudo ss -tulnp | grep :53

   Task 4) ¿Que IP tiene scanme.nmap.org y que servidor respondio?
       Primer intento con typo: dig scanme.namp.org
           status: NXDOMAIN, ANSWER: 0   → ese nombre NO existe
           AUTHORITY SECTION: namp.org. 600 IN SOA ns11.domaincontrol.com. ...
           → el dominio namp.org si existe y responde quien manda (registro SOA)
           Query time: 209 msec  (vs ~4 ms del router: el DNS esta en internet)

       Correcto: dig scanme.nmap.org
           scanme.nmap.org.   3600   IN   A   45.33.32.156
                 │             │     │    │        │
              nombre          TTL  clase tipo     IP
           SERVER: 200.21.200.10#53(200.21.200.10) (UDP)

       - Respuesta: 45.33.32.156, respondio 200.21.200.10 por el puerto 53 UDP.
       - TTL del DNS = SEGUNDOS que se puede guardar en cache la respuesta.
         (NO es el TTL del ping, que cuenta saltos entre routers.)
       - IN = Internet. A = nombre → IPv4.
       - dig viene en el paquete "bind" en Arch.

   Task 5) DNS inverso: ¿que nombre tiene 45.33.32.156?
       dig -x 45.33.32.156

       ;156.32.33.45.in-addr.arpa.    IN    PTR
       156.32.33.45.in-addr.arpa. 300  IN  PTR  scanme.nmap.org.

       - -x = reverse. Registro PTR: 45.33.32.156 → scanme.nmap.org.
       - La IP va AL REVES + .in-addr.arpa: asi guarda el DNS las busquedas inversas.
       - Esta es la misma consulta que hace Nmap por cada IP si no se usa -n.

   Task 6) DHCP: ¿que IP me prestaron, quien y por cuanto tiempo?
       nmcli device show enp8s0 | grep DHCP4   → no mostro nada (mi NetworkManager no
                                                  enseña esa seccion)
       nmcli device show enp8s0
           IP4.ADDRESS[1]:  192.168.1.20/24
           IP4.GATEWAY:     192.168.1.1
           IP4.DNS[1]:      200.21.200.10
           IP4.DNS[2]:      200.21.200.80
           IP4.WINS[1]:     192.168.1.1
       nmcli -f ipv4.method connection show "Wired connection 1"  → ipv4.method: auto

       ip -4 addr show enp8s0
           inet 192.168.1.20/24 brd 192.168.1.255 scope global dynamic noprefixroute enp8s0
              valid_lft 80874sec preferred_lft 80874sec

       - IP: 192.168.1.20/24 (privada; mascara 255.255.255.0 → red .1 a .254).
       - "auto" y "dynamic" = la IP la presto el DHCP (no puesta a mano).
       - Servidor DHCP: el router 192.168.1.1 (de ahi salen gateway, DNS y WINS).
       - valid_lft 80874 s ÷ 3600 = ~22,5 h RESTANTES (el prestamo seguramente es de
         24 h = 86400 s y ya habia pasado hora y media).

       Todo lo que entrego el router en un solo prestamo:
           IP + mascara   192.168.1.20/24
           Gateway        192.168.1.1
           DNS            200.21.200.10 y 200.21.200.80
           Duracion       ~24 h

   Task 7) NAT: ¿con que IP me ve internet?
       wget -qO- ifconfig.me

       Prepended http:// to 'ifconfig.me'
       190.xxx.xxx.xxx%        ← IP PUBLICA CENSURADA

       - -q = silencioso, -O- = sacar el resultado a la pantalla (curl tambien sirve).
       - El % final NO es de la IP: zsh avisa que la respuesta no termino en salto de linea.
       - Mi IP publica no se parece en nada a 192.168.1.20 → el router hace NAT:

           Mi PC                    Router (NAT)                    Internet
           192.168.1.20  ──────►  cambia el origen a  ──────►  ifconfig.me ve:
           (privada)              la IP publica                "me habla la IP publica"
                         ◄──────  y devuelve la        ◄──────
                                  respuesta a .20

       - La IP publica NO se pone en repos publicos ni se comparte.

   --------------------------------------------------------------------------------------------------
   Conclusiones del Tema 6
   --------------------------------------------------------------------------------------------------
       - Gateway = salida de la red (ruta "default" en ip route). El mio: 192.168.1.1.
       - DNS = nombres → IPs, puerto 53 (UDP normal, TCP para zonas/respuestas grandes).
         /etc/resolv.conf dice a quien preguntar; /etc/hosts es la agenda manual.
       - dig: ANSWER (respuesta), SERVER (quien respondio), status (NOERROR / NXDOMAIN).
         Registros A (nombre → IP) y PTR (IP → nombre, con dig -x).
       - Nmap hace PTR por cada IP → -n lo desactiva (mas rapido, menos ruido).
       - DHCP = el router PRESTA IP, mascara, gateway y DNS por un tiempo (lease).
         "dynamic" + valid_lft en ip addr.
       - NAT = el router cambia mi IP privada por su IP publica; desde afuera nadie puede
         iniciar conexion a mi PC sin pasar por el router.
       - Siempre usar | para encadenar comandos (ss | grep) y revisar typos (namp → NXDOMAIN).
